# Tracking model: where project state lives

How the [orca](README.md) skills expect a **consuming project** to track
roadmaps, milestones, and tasks. This is the source of truth for that design —
skills reference it rather than restating it.

> **This document does not apply to this repo.** `orca-skills` is markdown and
> JSON with no runtime and no parallel lanes; skill work commits straight to
> `main`. Everything below is about the projects the skills are pointed at. See
> [CONTRIBUTING.md](CONTRIBUTING.md) for how this repo works.

## The problem this solves

These skills push work into **separate worktrees running their own agents**. That
model breaks a tracked progress file in a specific way.

A roadmap file, status board, or `TODO.md` is a *single mutable file* that every
lane is told to update. Three lanes running concurrently means three worktrees
each editing the same file with no coordination:

- **Every PR conflicts.** Not occasionally — structurally, because every lane
  touches the same rows.
- **Worktrees disagree.** Lane B branched before lane A's row landed, so it
  reports stale state as current. Nothing is wrong with either lane; the file
  simply cannot represent two truths.
- **The bloat is a symptom.** A file that is both narrative ("why this milestone
  exists") and state ("done / in progress") can never be pruned — deleting a
  finished row deletes the reasoning with it.

Merge conflicts are the visible failure. The invisible one is worse: a lane that
resolves a conflict by keeping its own rows silently discards another lane's
progress, and no review step catches it.

## The model

State goes where concurrent writers are already safe — GitHub — and narrative
goes in append-only files.

| Concept | Home | Why there |
|---|---|---|
| Milestone | GitHub Milestone | A unit you'd finish and close, so progress is a derived count rather than a written number |
| Task | GitHub Issue in that milestone | Independent objects; two lanes touching two issues never conflict |
| Acceptance criteria | The issue's `### Done when` checklist | Written before the work, visible to planner, executor, and gate alike |
| Ready to start | Open issue with no unresolved `blocked-by` | Computed on read, so it cannot go stale |
| Status | Open / closed | Driven by `Closes #n` on merge — the merge *is* the state change |
| Progress notes | Issue comments | Append-only by construction |
| Plan / spec text | `docs/specs/<slug>.md` | Narrative belongs in the repo; append-only in practice, so safe to track |
| Roadmap | Generated, gitignored `ROADMAP.md` | A rendering of the above — never a source, so never a conflict |
| Lane state | Orca + `git` + `gh` | Orca tracks lanes natively; `/orca:status` joins them |

Three properties make this work:

**Nothing writes status.** Closing an issue is a side effect of merging a PR
whose body says `Closes #n`. No skill, lane, or human sets a status field. A
state machine with exactly one transition cannot disagree with itself.

**Truth is rebuilt, never stored.** `/orca:status` derives everything from
Orca/`git`/`gh` on each run and trusts no cached value.

**Criteria precede the work.** The `### Done when` checklist is written when the
issue is filed. A checklist written afterwards describes what happened; only one
written up front can gate anything.

### The stateless roadmap

`ROADMAP.md` is **generated from GitHub state and gitignored**. It is a view, not
a source:

```markdown
# Roadmap
<!-- GENERATED by /orca:status — do not edit; rewritten on every run -->

## v0.3 — Audio pass (4/11)
- [x] #48  Audio device enumeration
- [ ] #52  Footstep surfaces        in flight
- [ ] #55  Mixer ducking            blocked by #52
```

Why generated-and-ignored rather than committed:

- **No lane ever writes it**, so it cannot conflict — the failure this whole
  document exists to prevent.
- **It cannot drift**, because it is derived. Delete it and regenerate; nothing
  is lost, which is the test of whether a file holds state.
- **It is still a file** — scrollable, searchable, openable — which a terminal
  rendering is not.

A committed roadmap would reintroduce the conflict surface; the generated file
gets the readability without the state.

### Two things get called "the roadmap" — keep them apart

The most common confusion in a repo using this model, and worth naming directly:

| | The **plan** | The **tracker** |
|---|---|---|
| Example | `docs/roadmap.md`, a design record | `ROADMAP.md` (generated) |
| Holds | What the work *is*, why, in what order, what it depends on | What is done, in flight, next |
| Changes when | **A decision changes** | **Every run** |
| Written by | You | `/orca:status` |
| Tracked in git | Yes — it is narrative | No — gitignored |

Both are legitimate and a mature repo has both. What breaks is when one file
tries to be both — that is the tracked-progress-file problem at the top of this
document.

A planning doc that carries no status is **not** a violation of this model; it is
the narrative half working correctly. The test is whether it records *progress*.
"Task F2 depends on E1 and G2" is a plan. "Task F2 — in progress" is state that
belongs in the issue.

Worth stating in the planning doc's own header, so nobody has to infer it:

```markdown
> **This is the plan, not a status board.** It changes when a decision changes —
> not when work progresses. Live state is GitHub Issues; `ROADMAP.md`
> (generated, gitignored) renders that state.
```

### The narrative/state split

Roadmap bloat comes from mixing design thinking into a tracker, so keep them
separate on purpose:

- **`docs/specs/<slug>.md` is the narrative half** — why the work exists, the
  approach, the decisions and their rationale. Long-lived, append-only, reviewed
  like code.
- **Issues are the state half** — what is left, what is blocked, what is done.
  Short bodies plus a `### Done when` checklist. An issue body *links to* its
  spec; it does not restate it.

If issue bodies start growing design discussion, the roadmap is regrowing inside
GitHub and the split has failed.

### What makes a good milestone

Not necessarily a release. A milestone needs three properties:

- **You'd finish it and close it.** That is what makes the closed/total count
  mean something.
- **One is clearly active.** Skills resolve "the active milestone" as the open
  one with the nearest due date, so overlapping open milestones with no dates
  force a question every run.
- **Small enough to be a milestone.** Past roughly 25 open issues it is a bucket,
  and "% done" stops telling you anything.

Releases qualify, which is why they are the obvious example — but so do "Phase 2
— audio pass", "Vertical slice", or "Alpha playtest".

## What the skills do with it

- **`/orca:migrate`** brings a project into this model, and re-runs whenever the
  repo or the model has moved — after a plugin upgrade that changes what the
  skills expect, or as a drift audit. It is the on-ramp for everything else: the
  other skills consume the convention it produces.
- **`/orca:triage`** works a batch of raw issues into plannable ones, one at a
  time — asking what each means, what "done" looks like, when it is scheduled,
  and what it depends on. It is where the readiness contract gets populated:
  milestones assigned, `### Done when` checklists written, dependency edges
  recorded.
- **`/orca:wave`** plans several ready issues concurrently, one context each,
  then checks the finished plans against each other for file collisions — work
  that is independently ready can still overlap, and dependency edges cannot
  express that.
- **`/orca:plan`** accepts an issue number, milestone, or description, writes the
  `### Done when` checklist when it drafts, and never emits a step that writes
  progress to a tracked file.
- **`/orca:launch`** links the issue natively on the worktree and requires
  `Closes #<n>` in the executor's PR body — the transition the model rests on.
- **`/orca:status`** shows milestone progress, lane state, and a `READY NEXT`
  list of unblocked work — the read-only answer to "what should I work on next".
- **`/orca:verify`** checks the finished branch against the issue's own
  checklist. It is the only skill that reads criteria as *criteria*, and the
  reason they must be written up front.

## Required setup in a consuming project

**The easy path:** run `/orca:migrate` in the project. It audits what is there,
proposes migrating roadmap items to issues, narrative to `docs/specs/`, and
appends the rules below — proposing everything before it writes anything.

Re-run it later whenever either side has moved: after upgrading the plugin (the
model may now expect something new), or to catch drift. It records which schema
version it applied, so a later run knows the difference between a repo that is
current and one that merely was.

To do it by hand, paste this into the project's `AGENTS.md` or `CLAUDE.md` (a
plugin cannot write your project's always-loaded context, which is why this step
exists at all). The canonical copy — the one the skill transcribes — is
`plugins/orca/skills/_shared/agents-fragment.md`:

```markdown
## Task tracking
<!-- orca-skills tracking model v1 -->

- Task state lives in GitHub Issues. No tracked file records progress, status,
  or completion.
- Never edit a roadmap, status board, or TODO file to record progress.
- Every PR body includes `Closes #<n>`. Never close an issue by hand — if a
  merge did not close its issue, the PR body was malformed; report that.
- Progress notes go in issue comments, not files.
- Design and rationale go in `docs/specs/<slug>.md`. Issue bodies link to the
  spec; they do not restate it. A planning doc is the plan, never a status
  board — it changes when a decision changes, not when work progresses.
- Blocking is a real dependency, not a label or a prose line:
  `gh issue edit <blocked> --add-blocked-by <blocker>`. That edge is what
  readiness reads; a label mirrors it and can go stale.
- An issue with **no milestone** is the unscheduled backlog. Assigning a
  milestone is what scheduling means.
- Every issue carries a `### Done when` checklist of acceptance criteria —
  that checklist is what gates the work, and it is written when the issue is
  filed, not after the work is done.
- `ROADMAP.md` is generated from GitHub state and gitignored. Never edit it by
  hand and never commit it; regenerate it instead.
- Session-local planning scratch goes in a gitignored path.
- Confirm the active account with `gh auth status` before any `gh` write.
```

That last line is not boilerplate. `gh` can hold several authenticated accounts
with only one active, and the active one is whichever was selected last —
frequently the wrong one for a personal project. Check before writes, not after.

## Constraints and gotchas

Verified against `gh` 2.96.0 on a personal account, 2026-07-31. These look like
documentation lookups and are actually empirical questions, so re-verify rather
than trusting docs. Full detail in
`plugins/orca/skills/_shared/github-backlog.md`.

**Dependencies are readable in bulk — readiness is one call.** `blockedBy` and
`blocking` are available on `gh issue list --json`, not just `gh issue view`:

```bash
gh issue list --state open --limit 200 \
  --json number,title,milestone,labels,blockedBy,blocking
```

No fan-out, nothing to cache — which is what keeps `/orca:status` safe to loop.

**A `blocked` label is not a dependency.** Labels are decorative to every
readiness query; only real `blocked-by` edges are read. A backlog whose blocking
is expressed in labels will report everything ready — which is the honest reading
of that data, and a thing `/orca:migrate` flags.

**Issue types are org-level.** Personal-account repos cannot use them, so
classify with **labels** and never emit `--type`.

**Sub-issues are inconsistent on personal repos.** Do not build readiness on
parent/child hierarchy. The contract is *milestone membership plus dependencies*;
treat sub-issues as display-only enrichment when present.

**Guard the write, not the filename.** A tracked `ROADMAP.md` is not itself a bug
— a human-authored narrative roadmap is legitimate. What must fail is a skill
*writing progress into* a tracked file. (`/orca:migrate` is the exception that
*proposes* converting one, and it proposes rather than acting.)

**Verifying `--json` fields.** Ask for a bogus field (`gh issue list --json
nope`) and `gh` enumerates every valid one. Do not grep a filtered list and read
absence into it, and do not test on a repo with no issues — an empty repo returns
`[]` with exit 0, indistinguishable from an unsupported field.

## Non-goals

- **No GitHub Projects.** Milestone counts plus the generated roadmap are the
  board. Projects adds a schema to maintain for no state the model lacks.
- **No merge automation.** Lanes end at an open PR; a human merges. Since the
  merge is the only state transition, automating it would automate the one
  decision worth keeping.
- **No status field anywhere.** If a skill ever needs to *write* progress, the
  model has failed — re-read the first section.
